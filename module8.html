8.1 Data Layout & Memory Access Patterns

CFD performance is memory-bandwidth bound. Data layout determines cache utilization, vectorization, and parallel scalability.

Array of Structures (AoS) vs. Structure of Arrays (SoA)

// AoS: Poor vectorization, cache pollution struct Cell { double rho, rhou, rhov, rhow, rhoE; }; Cell cells[N]; // SoA: Contiguous, vectorizable, cache-friendly double *rho = new double[N]; double *rhou = new double[N]; double *rhov = new double[N]; double *rhow = new double[N]; double *rhoE = new double[N];

SoA is mandatory for SIMD/GPU. Use AoSoA (tiles of SoA) for L1 cache blocking: CellChunk { double rho[64], rhou[64], ... }.

Mesh Data Structures

  • Cell-centered: Cell arrays + face connectivity (cell-cell, cell-face)
  • Face-centered: Face arrays + cell-face incidence
  • Edge-based: Edge arrays for vertex-centered schemes

Store geometric data (volume, face area, normal, centroid, neighbor indices) in SoA. Precompute and store 1/volume, face_area/volume to avoid division in hot loops.

Ghost/Halo Layers

For distributed memory, each partition needs ghost cells from neighbors. Ghost depth = stencil radius (1 for 2nd-order FV, k for k-th order). Pack/unpack using MPI derived datatypes for non-contiguous data.

8.2 MPI Parallelization

Domain Decomposition

  • Partitioning: ParMETIS, PT-Scotch, Zoltan — minimize edge cut, balance cell count
  • Load imbalance metric: max_cells / avg_cells — target < 1.05
  • Communication volume: ∑ ghost_faces / ∑ owned_faces — minimize surface-to-volume ratio

Communication Patterns

OperationPatternOptimization
SpMV / Flux computationNearest-neighbor (halo exchange)Overlap comm/compute: MPI_Isend/Irecv + compute interior
Global reduction (dot, norm)MPI_AllreduceUse MPI_Reduce + broadcast for non-blocking; persistent collectives
Multigrid coarse solveAll-to-one or recursive halvingAgglomeration to fewer MPI ranks on coarse levels
I/OCollective MPI-IOHDF5/ADIOS2 with collective buffering

Overlapping Communication & Computation

// 1. Post non-blocking receives for ghost data MPI_Irecv(ghost_recv_buf, count, MPI_DOUBLE, src, tag, comm, &req[i]); // 2. Post non-blocking sends MPI_Isend(ghost_send_buf, count, MPI_DOUBLE, dst, tag, comm, &req[i]); // 3. Compute interior cells (no ghost data needed) compute_interior(); // 4. Wait for communication to complete MPI_Waitall(nreq, req, MPI_STATUSES_IGNORE); // 5. Compute boundary/ghost cells compute_boundary();

This hides latency; effectiveness depends on surface-to-volume ratio of partition.

8.3 Thread Parallelization (OpenMP, TBB, std::thread)

Loop-Level Parallelism

Parallelize over cells/faces/edges:

#pragma omp parallel for schedule(static) for (int i = 0; i < n_cells; i++) { compute_residual(i); }

static scheduling for uniform work; guided or dynamic for load imbalance (e.g., adaptive mesh, chemistry).

Thread-Safe Data Structures

  • Reductions: #pragma omp reduction(+:sum)
  • Atomic updates: For assembly into shared arrays (e.g., Jacobian)
  • Thread-local storage: Accumulate per-thread, reduce at end

MPI+OpenMP Hybrid

Typical: 1 MPI rank per NUMA domain / socket, OpenMP threads per core. Reduces MPI communication volume, improves memory locality. Set OMP_PROC_BIND=spread, OMP_PLACES=cores.

Key Kernels to Port

  1. Residual computation (SpMV-like): Flux loops over faces/cells — memory bound
  2. Reconstruction (least-squares): Small dense linear algebra per cell — compute bound
  3. Linear solver (SpMV, dot, AXPY): Krylov methods — memory bound
  4. Time integration stages: Vector updates — memory bound

Data Layout for GPU

  • SoA is essential — coalesced global memory access
  • Structure of Arrays of Structures (SoAoS): Tile of 32–128 cells per warp for shared memory
  • Avoid indirect addressing in hot loops — use compact neighbor lists or CSR with uniform stride
  • Unified Memory (CUDA) / USM (SYCL): Simplifies memory management; prefer explicit for performance

Preconditioners on GPU

  • Block Jacobi: Trivial — invert small dense blocks per cell in parallel
  • ILU(0): Hard — sequential dependencies; use level-scheduling or parallel ILU (e.g., PARILU, cuSPARSE)
  • AMG: Very hard — use AMGX (NVIDIA), hypre GPU, or Alpaka/RAJA AMG
  • Chebyshev / Polynomial preconditioners: Matrix-free, parallel — good alternative

8.5 Load Balancing for Adaptive & Multiphysics

Dynamic Load Balancing

For AMR, moving meshes, or chemistry: work per cell varies. Strategies:

  • Space-filling curves (SFC): Hilbert/Z-order — fast repartitioning, good locality
  • Diffusive load balancing: Iteratively migrate work to neighbors — low migration cost
  • ParMETIS repartitioning: Global repartition — high quality, expensive (do infrequently)

Multiphysics Coupling

Fluid-structure interaction, conjugate heat transfer, electrochemistry:

  • Monolithic: Single mesh, coupled Jacobian — best convergence, complex implementation
  • Partitioned (staggered): Separate solvers, data exchange at interface — modular, needs coupling iterations
  • Load balancing: Assign work based on compute cost per cell (fluid vs. solid vs. chemistry)

Best Practices

  • Collective MPI-IO: All ranks participate; enables file system striping
  • Chunked datasets: HDF5 chunks aligned with access pattern (time slices, spatial blocks)
  • Compression: ZFP (floating-point), SZ, Blosc — 2–10× reduction, fast
  • Asynchronous I/O: ADIOS2 engines (BP5, SST) — overlap I/O with computation
  • In situ: Extract QoI, render images, compute statistics during simulation — avoid writing full 3D fields

8.7 Performance Analysis & Optimization

Roofline Model

Plot achieved FLOP/s vs. arithmetic intensity (FLOP/byte). Ceiling: peak compute (CPU/GPU) and memory bandwidth.

  • Most CFD kernels: memory-bound (AI < 1 FLOP/byte)
  • Optimization target: increase AI via fusion, tiling, recomputation

Profiling Tools

  • CPU: perf, VTune, PAPI, HPCToolkit, TAU, ARM MAP
  • GPU: Nsight Compute, Nsight Systems, rocprof, CUPTI
  • MPI: MPIP, Intel MPI Trace Analyzer, Vampir, Scalasca
  • Hardware counters: L1/L2/L3 miss rate, memory bandwidth, occupancy, SM throughput

8.8 Reproducible Computational Workflows

Build Systems & Dependency Management

  • CMake + CTest + CDash: Standard for C++/Fortran HPC
  • Spack: Package manager for HPC — builds dependencies (MPI, HDF5, hypre, etc.) reproducibly
  • Containers: Apptainer/Singularity (HPC-friendly), Docker (dev) — capture full environment

Version Control for Code & Data

  • Code: Git — semantic versioning, signed commits
  • Large data: Git-LFS, DVC, or object storage (S3, iRODS) with checksums
  • Mesh/Input decks: Version with code (small) or DVC (large)

Continuous Integration for HPC

  • Compile test on target architectures (CPU, GPU)
  • Unit tests (GoogleTest, Catch2) for math kernels
  • Regression tests: run small cases, compare QoI to reference (tolerance-based)
  • Performance tests: track FLOP/s, memory bandwidth, time-to-solution

Provenance & Reproducibility

Every simulation result must record:

  • Git commit hash (code version)
  • Input deck (parameters, mesh)
  • Container hash / Spack spec (environment)
  • Hardware (node type, GPU model)
  • MPI/OpenMP/GPU configuration (ranks, threads, affinity)
  • Random seeds (for stochastic methods)

Tools: ReproZip, Sumatra, MLflow, Sacred for experiment tracking.

8.9 Scaling to Leadership-Class Systems

Strong vs. Weak Scaling

  • Strong scaling: Fixed problem, more cores — target: T(P) ≈ T(1)/P. Limited by communication overhead, Amdahl's law.
  • Weak scaling: Fixed problem per core, more cores — target: T(P) ≈ constant. Limited by global reductions, I/O, load imbalance.

Exascale Challenges

  • Resilience: MTBF ~ hours at 1M+ cores — checkpoint/restart, algorithm-based fault tolerance (ABFT)
  • Energy: Performance per watt — lower precision (FP16/BF16), near-data processing
  • Heterogeneity: CPU + GPU + accelerator — portable programming models (Kokkos, RAJA, SYCL)
  • Memory hierarchy: HBM, DDR, CXL, NVRAM — data placement, tiered memory

CFD-Specific Exascale Efforts

  • ExaWind (NREL): Wind farm simulation, AMReX-based
  • CEED / NekRS: High-order spectral elements, GPU-native
  • AMReX / BoxLib: Block-structured AMR, GPU-ready
  • MFEM / libParanumal: High-order FEM, GPU
  • OpenFOAM GPU / CFD-GPU: Finite volume on GPU

8.10 Capstone: Mini-CFD Solver Architecture

A modern, performant CFD solver structure:

src/ ├── core/ # Mesh, fields, parallelism, timer, logging │ ├── mesh.{h,cpp} # Unstructured mesh, partitioning, ghost exchange │ ├── field.{h,cpp} # SoA field data, halo exchange, reduction │ ├── parallel.{h,cpp} # MPI + OpenMP + GPU abstraction │ └── timer.{h,cpp} # Scoped timers, hardware counters ├── physics/ # Equations, models, boundary conditions │ ├── euler.{h,cpp} # Inviscid fluxes, Riemann solvers │ ├── navier_stokes.{h,cpp} # Viscous fluxes, turbulence models │ ├── reconstruction.{h,cpp} # WENO, LSQ, limiters │ └── boundary.{h,cpp} # BC types, characteristic BCs ├── numerics/ # Time integration, linear solvers │ ├── time_integrator.{h,cpp} # RK, IMEX, BDF, dual-time │ ├── linear_solver.{h,cpp} # Krylov, preconditioners, AMG interface │ └── newton.{h,cpp} # Newton-Krylov, JFNK, globalization ├── io/ # Checkpoint, output, in situ │ ├── checkpoint.{h,cpp} # HDF5/ADIOS2, async │ └── output.{h,cpp} # VTK, Tecplot, in situ (Catalyst) ├── driver/ # Main, parameter parsing, workflow │ ├── main.cpp │ ├── parameters.{h,cpp} # JSON/YAML input, validation │ └── workflow.{h,cpp} # V&V, UQ, optimization drivers └── test/ # Unit, regression, performance tests ├── unit/ ├── regression/ └── performance/

Key Design Principles

  1. Separation of concerns: Physics independent of parallelism, discretization, hardware
  2. Abstraction without overhead: Templates/policies for backend (CPU/GPU), zero-cost at compile time
  3. Testability: Every kernel unit-testable; manufactured solutions in CI
  4. Extensibility: New equations, models, BCs without rewriting core
  5. Reproducibility: Provenance tracking built into driver

Socratic Questions

Question 1: For a 3D unstructured FV solver with 5 conserved variables per cell, compare the memory bandwidth requirements (bytes/FLOP) for AoS vs. SoA layout when computing the inviscid flux over all faces. Assume each face flux reads 5 variables from each of 2 cells, performs ~100 FLOP, and writes 5 fluxes. Which layout achieves higher fraction of peak bandwidth on a GPU with 1.5 TB/s memory bandwidth?

Question 2: In a 3D MPI+OpenMP hybrid solver with 64K cells per rank, the halo exchange communicates 8K doubles. The interior computation takes 2 ms, the boundary computation takes 0.5 ms, and the MPI latency + bandwidth cost is 0.8 ms. If you overlap communication with interior computation, what is the total step time? What fraction of the communication is hidden? How does this change if the interior work drops to 0.6 ms (e.g., at scale)?

Question 3: You are porting the least-squares gradient reconstruction kernel to GPU. Each cell gathers data from ~20 neighbors, forms a 5×20 matrix, computes QR factorization, and solves for the gradient. Analyze the challenges: (a) irregular memory access, (b) small dense linear algebra, (c) divergent control flow. Propose a strategy using warp-level primitives and shared memory to achieve >50% occupancy.

Question 4: In an adaptive mesh refinement (AMR) simulation with 4 refinement levels, the finest level has 10× more cells than the coarsest. The work per cell is proportional to the level (due to smaller time steps). Design a space-filling curve (SFC) based load balancing algorithm. How do you weight the SFC keys to account for variable work per cell? What is the migration cost vs. ParMETIS repartitioning?

Question 5: You run a production simulation on 1024 GPUs for 48 hours. The result is a drag coefficient C_d = 0.02341. Six months later, you need to reproduce it exactly. List the minimum set of metadata you must have archived. If the original GPU model (A100) is no longer available and you must run on H100, what aspects of the result might change despite identical code and inputs? How would you quantify this?
